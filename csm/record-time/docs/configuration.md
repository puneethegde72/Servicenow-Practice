# Record time configuration

## Custom application

Create the custom component in an application you control. Replace `x_your_scope` in the source with its actual scope. Configure any required access to Task, Time Worked, Customer Project and Case tables through the normal application access and cross-scope mechanisms.

## Required data model

The source uses these `task_time_worked` fields:

| Field | Use |
|---|---|
| `task`, `user`, `work_date` | Task, signed-in user and work date |
| `time_in_seconds`, `time_worked` | Duration in seconds and duration value |
| `category`, `comments` | Optional entry details |
| `u_time_slot` | Custom choice field with consecutive one-hour values such as `08_09`, `09_10`, `10_11` |
| `u_area_of_work` | Custom choice field; configure your own active choices |
| `u_reporting_project` | Optional reference to `customer_project` |

Create and validate custom fields before installing the UI Page. Do not use overlapping, multi-hour or overnight slots with the example's one-hour capacity rule.

## Script Include

- Name: `PracticeTimeEntryAjaxV2`
- API name: your actual scope followed by `.PracticeTimeEntryAjaxV2`
- Active: true
- Client callable: true
- Accessible from: the minimum scope access needed by your UI Actions and UI Page
- Script: `../source/script-includes/PracticeTimeEntryAjaxV2.js`, relative to this guide

Configure the client-callable access/role controls supported by your instance. The source checks Task read access and Time Worked create access with `GlideRecordSecure`. Validate field write ACLs for the intended users; hiding the button is not a server-side access control.

## UI Page

- Name: `practice_record_time_v2`
- HTML: `../source/ui-page/practice_record_time_v2.html`
- Client Script: `../source/ui-page/practice_record_time_v2.client.js`
- Processing Script: blank
- Example endpoint: `/x_your_scope_practice_record_time_v2.do`

Confirm the actual endpoint generated by your instance. Restrict UI Page access to the intended time-recording users.

## UI Actions

Create your own actions on `customer_project` and/or `sn_customerservice_case`, if those tables are installed. Use the matching scripts in `../source/ui-actions/`.

| Setting | Customer Project | Case |
|---|---|---|
| Name | Record Time | Record Time |
| Action name | `practice_record_time_v2` | `practice_record_case_time_v2` |
| Onclick | `openPracticeProjectRecordTime()` | `openPracticeCaseRecordTime()` |
| Classic script | `customer-project-record-time.client.js` | `case-record-time.client.js` |
| Workspace script | `customer-project-record-time.workspace.js` | `case-record-time.workspace.js` |

Enable Client and the appropriate form/Workspace options for your release. Show the action on saved records only and restrict visibility to your intended roles. Configure an example condition such as `!current.isNewRecord() && gs.hasRole('YOUR_TIME_RECORDING_ROLE')` after replacing the role placeholder. Validate that each user also passes the server-side ACL checks.

## Instance validation

1. Confirm the modal opens from a saved Customer Project and Case in Classic UI and Workspace.
2. Confirm the UI Page calls the correct scoped Script Include.
3. Confirm a permitted user can create the required fields and an unauthorised user cannot submit entries.
4. Check a partial slot, a full slot, several staged entries, a gap between slots and a duration beyond the final slot.
5. Confirm invalid dates, invalid choices and invalid Task references are rejected.
6. Confirm successful rows reference the current Task and signed-in user, with the expected total duration.
7. Exercise insertion failure and inspect cleanup and downstream business-rule/notification behaviour.
8. Test simultaneous submissions if strict slot capacity is a requirement. Add a locking or data-model solution before relying on that limit under concurrency.
